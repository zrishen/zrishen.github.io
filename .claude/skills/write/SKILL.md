写中文文章（随笔、技术文皆可）。

**优先级**：用户当次指令 > 本文件规则；本文件内部新旧规则冲突时，以最新的为准。

结构以用户为准：用户给了大纲或链条，就严格按用户的结构写；自己的结构修正意见先提出来和用户讨论，用户拍板后再动笔，不擅自重构。

## 载体与流程

- 文章：`src/content/blog/<slug>.md`，slug 用英文 kebab-case
- frontmatter 三项：`title`（中文标题）、`date`（如 `2026-10-14`）、`description`（一句话摘要；第一人称引子风格：先说情境，破折号接出这篇在讲什么）
- 正文用 `##` 分节（自动进文章页左侧目录），不写 `#` 一级标题（文章标题来自 frontmatter）
- 图片放 `public/images/`，文件名用描述性英文 kebab-case；正文用 `/images/xxx.png` 绝对路径，alt 用中文；插图紧跟描述它的段落之后
- 首页列表、归档和文章目录自动收录，不用额外登记
- 动笔前先读 1~2 篇已发布文章作风格基准

## 渲染约定（正文按这些写法来）

- 正文以段落承载；分点列表可用（`-` 分点，样式已配），表格、引用、代码块没有样式，别用
- 上下标用 HTML：`w<sub>1</sub>`、`QK<sup>T</sup>`
- 独立公式块：`<p class="formula">…</p>`——居中、单行、窄屏横向滚动；同类式子可用 `<br>` 分行放进同一个块
- 分数、根号这类公式用 MathML（`<p class="formula"><math display="block">…</math></p>`），别拼 Unicode 字符。两条铁律：**不要用 CSS 给 `<math>` 写 `display`**（会把数学排版关掉，`mi`/`mo`/`mfrac` 竖着堆成一列）；**不需要拉高的括号写 `<mo stretchy="false">`**，否则它会跟着同一行的高元素一起被撑大
- 链路/流程：`<p class="roadmap">A → B → C</p>`——单独成行、居中加粗
- 插图写 HTML：`<img src="/images/xxx.png" style="width: 100%" alt="…">`，紧跟描述它的段落之后；图下加一行 `<p class="caption">……</p>` 做图注（小字居中灰），说明图是什么、和正文哪句对应，英文图要补中文说明
- `style="width: X%"` 是插图尺寸唯一的旋钮，X 相对正文栏宽度（100% 约等于栏宽），长图短图各自调；宽高属性由 `astro.config.mjs` 的 rehype 插件按图片实际尺寸自动补，别手写
- 现有插图仅要求高清化时，保留原图配色、布局、标注与连接关系；只有明确要求重新设计的图才调整视觉风格，同一批图片逐张区分处理范围
- 正文链接可用（`[文字](url)`，外链自动新标签页；平时无下划线、悬停出现）；论文、方法、模型、术语首现都要带上出处链接（论文页或官方页），别让读者自己搜
- 加粗用 markdown `**…**`；粗体句后面紧跟中文正文时，句末标点要放到粗体外（写成 `**……**。` 才解析得出；`**……。**` 后面直接跟字会失效）
- 红色主线强调用 `<span class="highlight">……</span>`；使用范围与次数按下方对应场景的风格规则执行

## 写完的验证

1. 执行 `npm run build`，确认生产构建成功；构建报错先定位并修复
2. **自己用 Playwright 看渲染结果，不要让用户替你检查**：`playwright-core` 装在临时目录（不进项目依赖），驱动本机已装的 Edge——`chromium.launch({ channel: 'msedge' })`，无需下载浏览器。桌面按 1500×1050、窄屏按 400×900 各截一轮
3. 核对：桌面端正文小标题与左侧目录一致、锚点可跳转；公式（含 MathML）渲染正确、不折行，窄屏下超宽公式可在块内横向滚动、不撑宽整页；插图正常加载、位置正确且不超出正文宽度
4. 关键区域截图给用户过目后再收尾；发现渲染问题当次修掉，修改后重新构建并复核受影响区域
5. 用脚本批量改正文：先备份，改完立刻 `git diff` 逐行核对范围。**不要用带 `re.S` 的跨行贪婪匹配**——`.+?` 会从文件里第一个 `<img` 一路吞到目标位置，一次误删几节正文
6. 改了 `astro.config.mjs`（插件、样式配置）而文章内容没动时，效果可能不出现：内容层把渲染结果缓存住了。删掉 `node_modules/.astro` 再重启（只改文章内容会自动重渲染）

6. 短段落、口语化叙述，像跟人讲，不端腔
7. 技术事实必须准确（年份、论文、人名、参数量、术语及历史因果），动笔前核对，拿不准先查证，不编造；事实准确性优先于叙事顺畅和演进链条，不能为了串起主线补造因果关系
8. 正文里破折号（——）不要到处用：最多开头点睛句留一处，也可以一处不用，其余用逗号、句号或拆句自然表达
10. 讲概念或问题，用最短的话说清：因果链说全，抽象处配一个简短例子，例子要卡进对应环节、把因果走完，不悬在外面；少用「学过的」「数出来的」这类虚指的说法，换实指的词；清楚靠组织逻辑和用词，不靠堆字
13. 不贬评前人的工作：不用「天真」「幼稚」「粗暴」这类评价词，结合当时的条件说明方法的作用，不默认它是当时最优的解法；讲缺陷只说客观局限（如「它的局限也在这里」）
14. 表述落到具体动作和对象：别用诗意抽象的说法（如「把历史藏进一个隐状态」），换成「把读过的词记进一个状态」这类人话
15. 剔除 AI 感：套话式收束（如「一套结构就齐了」）、拔高式收尾（如「撑起了我们叫做智能的东西」）都不要，结尾落回具体的东西
16. 删重复：同一件事不在相邻两段说两遍；改完一段再看一眼上一段是不是已经说过
17. 润色不动作者的原词、不挪作者的重点：有分量的概念词（如「通才/专才」「知识广度」「信息整合能力」）一律保留，换成大白话等于稀释观点；作者要强调什么（如「大脑并行」），改完还是强调什么，别让补充的洞察喧宾夺主
18. 非技术文同样要有深度：随笔、观点文不能只把想法通俗化转述，每个点要给一个机制或判断（为什么现在成立、什么被替代了、分水岭在哪），让读者看到作者自己的思考
19. 删句标准：一句话删掉之后，读者的理解不变，那它就是废话，删。定稿前逐句过一遍这一关：正说一遍又反说一遍的、同义换词的、把结论复述一遍的，都在删列

技术文专属：

1. 开头先交代全文主线（总-分：先总述再展开）；文章有链条/流程时（如 A → B → C），链条单独成行、居中加粗，紧跟总述句
2. 小节标题只写名字本身，不带「标题：一句加注」这类冒号后缀；想加的定位描述融入该节第一句或最自然的位置
4. 关键公式独立成行（用 `<p class="formula">`），永不折行；同类的一组式子可以用 `<br>` 分行放进同一个块
5. 演进/链条类：每节承上启下，交代要解决的问题 → 这一方法怎么做 → 仍有或新引入的局限；有来源支持的继承关系才写成「上一代瓶颈推动下一代」，并行发展或后来结合的路线明确说明，区分讲解顺序与真实历史顺序
9. 并列的枚举（几个毛病、几条对比、几件事这类）用 `-` 分点写，条目标签用规范术语、几条之间结构对仗，全文的标签风格保持一致（如都走「对象+状态」的四字式）；条目是完整句子的，末尾统一加句号；收尾句独立成段，不混进列表
11. 每个部分在开头部分挑一处加粗：只加粗关键的那截短语（如「不数了，学。」），不整句加粗；全文形成可扫读的加粗骨架；红色的主线强调全文只留一处
12. 缩写首次出现给英文全称：「中文名（English Full Name，缩写）」或「缩写（English Full Name）」；每个部分里各自交代一次，不依赖前文
15. 演进类文章时间线要顺：给每个阶段钉时间锚；某事的发生时间早于前文提过的内容时，明确说明（如「比上面那些应用还早」），别让读者自己对着年份来回绕
16. 少出现人名：除非公认很出名（如 Bengio 这个级别），否则不写「某某提出」，直接写成果（attention、LSTM），出处由链接承担
17. 新术语首现要顺手交代角色（如「做法就是一读一写，编码器……解码器……」），别让它突然出现、让读者猜它是干嘛的
18. 讲机制时例子当主干，不是点缀：先给一个具体输入（如一句话），按「输入是什么 → 各部分之间怎么相互作用 → 反复叠加计算 → 输出变成什么」的顺序走完，讲透之后再上公式和缩写；Q/K/V、矩阵形状这类术语往后放，别一上来就摆
19. 例子要贴读者熟悉的使用场景（如「给 AI 一句话，它回一句话」），输入和输出成对写出、看得出差别；「输出是什么」必须写具体，别用「读懂之后的样子」这类抽象说法
20. 同一类数据要么全用同一形式列出（比如每个词一条配比），要么不列；别一部分进公式块、一部分散在句子里
21. 收尾小节的标题用「总结」

## 反馈闭环

- 用户对文章的每次纠正都是风格输入：立即改正当次；可泛化的（换一篇文章仍成立）沉淀进「风格」一节对应场景的组（通用 / 技术文专属）；场景拿不准先问用户；一次性内容修正（只属于某篇的措辞或事实）不动本文件
- 风格迭代不只是追加：与最新反馈冲突的旧规则要直接改掉或删掉，不能只叠新条
- 改前先分场景：新旧规则若属不同场景（如正文 / 描述行、技术文 / 随笔、演进类 / 其他），各自保留并注明适用场景；同一场景内真冲突，才以最新为准、改写或删除旧条，不并存矛盾
- 出现新场景先查组：遇到新的文章类型（随笔、叙事、访谈这类），先看「风格」里有没有对应的场景组；没有就新开一组（组名 + 适用说明），之后该场景的规则都沉淀进自己的组
- 本文件面向 AI 执行：措辞以可执行、可匹配为准，不按人类阅读观感取舍
- 写完向用户报告：写了什么、本次是否沉淀新规则
